## Step 0 — the instrument

`verify/attr_options_gt.py` decided a merge with one arithmetic test per LOG ROW. The node requires
the same PAIR to hold above the threshold on `merge_min_consecutive` successive scored sweeps,
breaks that streak on a room or geometry refusal, applies the unwitnessed-overlap rule, and answers
once per pair. The tool now deletes its copy of that logic and calls `association.Hypothesis` and
`association.PairScore` directly; `merge_min_consecutive`, `merge_min_evidence` and the threshold
come from `config.yaml` and from the row, never from a literal in the tool.

**The predicted collapse is confirmed, exactly.**

| bundle | GT-true duplicate pairs | merges reported BEFORE | merges AFTER |
|---|---:|---:|---:|
| `20260914_180343_hm3d_00824` | 20 | 16 across five options | **1** |
| `20260914_174342_hm3d_00824` | 6 | 13 across five options | **0** |

Recall on 180343 moves from 0.15 / 0.15 / 0.15 / 0.25 / 0.10 to 0.00 / 0.00 / 0.00 / **0.05** / 0.00.
The single surviving merge is `plant <-> plant`, ground-truth TRUE (`flower vase_21`), under `ref075`.
Precision prints `nan` for the other four options: with zero merges it is undefined, not high.

**A second defect, one level down, found by the new self-check.** The tool's `attr_llr` was itself a
copy of `association.channel_attributes`, and the shipped rule had moved under it: the owner's
same-kind floor of that morning. Measured over the 97 recorded attribute rows of the two runs, the
copy differed from the engine on **3 of 50** rows of 180343 — each a same-kind pair where the engine
returns 0.0 and the copy returned about −3.8, a 3.88-nat error on the arm the whole table is read
from — and drifted by up to 0.01 nats on **54 of 97** rows, because it recomputed from `score`, which
the record rounds to four decimals. `attr_llr` is now retired in place, with that measurement in its
docstring, and the options are arguments to the engine's own function. The `shipped` column is not
recomputed at all: it is the number the run recorded, so the baseline is an exact replay by
construction and cannot drift from the node again.

**The option names changed** because the old ones named a rule that no longer ships:
`current -> shipped`, `floor0 -> ` (dropped: it IS the shipped rule now), `floor1` and `ref075` kept,
`off` kept, and a new `no_floor` arm. The `co-visibility rule` rows are relabelled
`veto 2D only (shipped)` and `veto needs 3D too (withdrawn)` after the 2026-09-14 revert.

**The denominator is swept, not chosen.** Recall now prints at assignment-IoU floors 0.00 / 0.05 /
0.10 / 0.25 / 0.50 with its own `n` on every line, plus a same-base-label line. On 180343 the pair
count runs 20 / 13 / 11 / 4 / 0 and the same-label count is 13. No floor is adopted.

### One additive telemetry key, in production

wording. A new key cannot break a reader that does not look for it (working rule 6). Until a run
writes it, the tool reconstructs the flag from the two reason strings that set it, and says so.

## 1a — self-scale collapse (4 edits)

- **E1**, `association.position_covariance`: when nothing measured the position — no
  `depth_sparsity`, no `pose_sigma_m`, and an observed spread at or below the function's own 1e-9
  floor — it returns `None` instead of the floor. Its docstring already forbade the floor. All three
  consumers already had a written path for `None`.
- **E2**, `object_manager_6._record_sighting`: the Observation records this frame's box centre, not
  `obj.centroid`. `Object.centroid` is assigned once at creation and by no later code, so every
  Observation of one object held one identical point and the sample covariance was exactly zero.
- **E3**, `object_services` and `object_manager_6`: `centroid=` is no longer passed to `AssocObject`,
  so it derives the centre from the box being scored rather than from where the object was first seen.
- **E4**, `AssocObject.descriptor_spread`: the L2 norm of the per-component deviations, not their
  mean. `channel_appearance` divides a full-vector L2 distance by this scale, so the mean was smaller
  by about `sqrt(dimension)` — 22.6 on a 512-d CLIP vector.

Measured cause, two runs, 139 refusal rows of which 97 carry channel values: the separation channel
sat at exactly −8.0 on **41 of 41** scored rows, implied covariance exactly 4.000e-9 on 39 and
3.500e-9 on 2 — the exact output of the zero-spread branch. Appearance: **3 of 3** rows at −8.0.

**Not done on purpose:** `depth_sparsity` and `pose_sigma_m` stay unpassed. They are real sensor
quantities and no value has been measured on this robot. Wiring in a guess would rebuild the same
lie in a wider form.

**What it arms, and this is the largest item in the whole change set.** With the covariance `None`,
`object_manager_6.tracking_reach_m` restores `TRACKING_FALLBACK_RADIUS_M` — 1.0 m, never measured,
absent from `config.yaml`. Reach per object goes from half-diagonal + 0.15 mm to half-diagonal + 1.0 m.
Bounded on the GA-493 replay, 104 objects, 10,712 ordered pairs: reachable pairs 532 -> 1,408;
same-base-label 174 -> 336. Those extra pairs land on an association decision measured at 0.24 recall
and 54 duplicate adds out of 119 calls — weak in BOTH directions. The false-association risk is newly
exposed and is measured nowhere. The 532 -> 1,408 figure is itself computed from the FINAL persisted
boxes, and the lane already withdrew a different claim for exactly that reason, so treat it as a
bound, not a measurement.

## 1b — the attribute channel, muted on same-kind pairs

`channel_attributes` now tests `same_kind` FIRST, so the mute catches the positive arm as well as
the negative one the owner's floor already removed. The cross-kind arms are untouched: that is where
the channel does separate. One additive detail key, `same_kind_muted`, so a bundle says the channel
was muted rather than that it looked and scored zero.

Measured on the GA-493 final map (104 objects) and the two runs: on a same-label pair the composite
is `0.85 + 0.15*c` by construction — the three string terms sum to exactly the reference and read 1.0
on 244 of 312 known-different same-label pairs — so the score could never fall below the reference
and the channel could only vote FOR the merge. It did, on **249 of 312 known-DIFFERENT** pairs, at a
median **+1.13 nats**, 37.8 % of the commit threshold. A pair whose descriptions were not comparable
scored exactly 1.0 and took the full +2.0 ceiling: the least informed pair received the largest vote.
As an instance discriminator: AUC 0.5324 (geometry proxy), 0.5127 (ground truth), 0.3461 (ground
truth with an IoU floor of 0.1) — at or below chance.

`same_kind_floor_zero` and its config key are kept and no longer gate anything; the docstring says so.

**One existing assertion was corrected, not deleted** (`opted_out == cross_kind_low` -> `== 0.0`),
because opting out of the floor can no longer restore the negative arm.

## 1c — a veto is re-measured, not remembered

`Hypothesis.update` REPLACES `vetoed_by` each sweep, the same rule `self.state` three lines below
already followed. It used to append to a list nothing ever cleared, while `_hypothesis_gc` deletes
the whole hypothesis — veto included — for any pair not re-offered: two contradictory persistence
policies, and which applied was decided by re-offer luck. The veto still wins on the sweep it fires
(`total` is −inf, `decide` answers `reject`, the streak breaks); it no longer outlives its own
measurement. The history entry's `total` no longer reads `self.total`, because −inf is not valid JSON
for a strict reader; `veto` is now on every entry, empty when nothing vetoed. One additive record key,
`total_if_unvetoed`, so a vetoed row says how close the pair came.

Measured: the veto fires on **41 of 97** scored rows (42.3 %), covering 37 of 116 distinct pairs.
Effect on today's outcomes: **0 of 41** — nothing it blocked reaches the threshold on the other
channels (maximum 2.60 against 2.9957). The population this repairs has size **zero** in every bundle
on disk, because no bundle has enough sweeps.

## 1d — the merge apply block

New `object_services._absorb_into_keeper`, called inside the locked apply block before the discard
leaves the map. The survivor inherits the discard's `observations`, deduplicated on `frame_id`,
time-ordered, capped by the same `max_observations_per_object` key `_record_sighting` already reads;
and its `centroid` is rewritten to the merged box's centre. `observations` is the sole input of
`position_covariance`, `channel_covisibility` and the appearance descriptors, so a merge used to make
the map LESS able to reason about the object it had just consolidated. The move path always did this;
the merge path never did.

`"bbox_source": "keeper"` is corrected to `"union_hull"`. It was true when the key was added on
2026-09-01 and stopped being true when the hull write was restored. No reader consumes the value.

**The union-hull write itself is deliberately NOT changed.** It is the tree's standing geometry
policy — the ordinary update path unions the same way and no path ever shrinks a box — and its cost
is only knowable from a run that applies merges. There are none on disk.

**What it arms:** a keeper that inherits the discard's frames becomes co-visible with every third
object that shared a frame with the DISCARD and never with the keeper. All 41 co-visibility vetoes in
the two runs fired at `n_covisible = 1`, so one inherited frame is enough. Direction: this can only
ADD vetoes.
